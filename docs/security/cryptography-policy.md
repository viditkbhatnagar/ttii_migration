# Cryptography Policy

**Version:** 1.0 (draft) | **Effective Date:** {{EFFECTIVE_DATE}} | **Owner:** Engineering Lead
**Last reviewed:** {{LAST_REVIEW_DATE}} | **Next review:** {{NEXT_REVIEW_DATE}}

This policy specifies the approved cryptographic algorithms, key-management practices, and protocols used by the TTII Platform.

## 1. Approved primitives

### 1.1 Password hashing

| Use | Algorithm | Parameters | Source |
|---|---|---|---|
| Password storage | **scrypt** | `N=16384, r=8, p=1`, key length 64 bytes, salt length 16 bytes (random per password) | [`apps/api/src/auth/password.ts`](../../apps/api/src/auth/password.ts) |
| Legacy verification only (from the previous PHP application) | bcrypt (`$2a$`, `$2y$`, `$2b$`) | As stored historically | [`apps/api/src/auth/password.ts`](../../apps/api/src/auth/password.ts) |

After successful verification of a legacy bcrypt hash, the password is rehashed with scrypt. **No new bcrypt hashes are written.**

### 1.2 Hashing for non-password use

| Use | Algorithm |
|---|---|
| Session-token at-rest fingerprint | SHA-256, hex-encoded |
| OTP at-rest fingerprint | SHA-256 |
| Password-reset email fingerprint inside the reset token (`eh`) | SHA-256 |
| Password-hash-fingerprint inside the reset token (`pwh`) | First 24 hex chars of SHA-256 |

MD5 and SHA-1 must not be used for any new code path. If existing code uses them, raise a ticket to remove.

### 1.3 Symmetric / authenticated encryption

| Use | Algorithm |
|---|---|
| HMAC for password-reset token signing | HMAC-SHA256 with the `PASSWORD_RESET_TOKEN_KEY` secret |
| HMAC for OTP derivation / verification | HMAC-SHA256 with the `OTP_SIGNING_KEY` secret |
| HMAC for storage signed-URL derivation | HMAC-SHA256 with the `STORAGE_LOCAL_SIGNING_KEY` secret |
| Future column-level encryption (e.g., Aadhaar) | AES-256-GCM with a key managed separately (target state — see [Aadhaar Handling Policy](../compliance/aadhaar-handling-policy.md)) |

### 1.4 Asymmetric primitives

Used implicitly by TLS (the certificate authority chain) and by upstream providers (Microsoft Graph OAuth, Razorpay TLS). Internally we do not currently mint asymmetric keys.

### 1.5 Random number generation

All cryptographic randomness is generated by `node:crypto` (`randomBytes`) which is backed by the OS CSPRNG. `Math.random` must not be used for any security purpose.

### 1.6 Transport security

| Where | Standard |
|---|---|
| Browser ↔ TTII | TLS 1.2 or higher, terminated at nginx with a Let's Encrypt SAN certificate |
| TTII API ↔ MariaDB | Private VPC at `10.122.0.2:3306`. MariaDB native protocol (target: explicit TLS) |
| TTII API ↔ object storage | TLS to {{OBJECT_STORAGE_PROVIDER}} (S3-compatible) |
| TTII API ↔ Razorpay | TLS to `api.razorpay.com` |
| TTII API ↔ Microsoft Graph | TLS to `graph.microsoft.com` |
| TTII API ↔ Brevo / SMTP / Microsoft Graph email | TLS |

> ⚠️ **Known gap:** the MariaDB connection string (`DATABASE_URL`) does not currently enforce TLS at the protocol level. Because the link is on a private VPC the practical exposure is low, but enabling MariaDB TLS is on the roadmap.

## 2. Key management

### 2.1 Where keys live

All long-lived secrets live in environment variables on the production droplet (`/etc/.../app.env` or equivalent), readable only by the application user. Secrets are **never** committed to the repository. The example file [`apps/api/.env.example`](../../apps/api/.env.example) lists every secret name with **placeholder** values; production values are set on the droplet by Engineering Lead-approved staff only.

The current set of cryptographic secrets:

| Secret | Purpose |
|---|---|
| `PASSWORD_RESET_TOKEN_KEY` | HMAC-SHA256 key for password-reset tokens |
| `OTP_SIGNING_KEY` | HMAC-SHA256 key for OTP derivation |
| `STORAGE_LOCAL_SIGNING_KEY` | HMAC-SHA256 key for local-storage signed URLs |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | Object storage credentials |
| `PAYMENT_RAZORPAY_KEY_ID` / `PAYMENT_RAZORPAY_KEY_SECRET` / `PAYMENT_RAZORPAY_WEBHOOK_SECRET` | Razorpay |
| `EMAIL_BREVO_API_KEY` / `EMAIL_SMTP_PASSWORD` / `EMAIL_MSGRAPH_CLIENT_SECRET` | Email |
| `OTP_HTTP_AUTH_TOKEN` | SMS-OTP provider |
| `ZOOM_SDK_KEY` / `ZOOM_SDK_SECRET` | Zoom SDK |
| `OPENAI_API_KEY` | OpenAI |

### 2.2 Generation

Keys at the TTII boundary (HMAC keys, storage signing keys) are generated locally as 32+ bytes of `randomBytes` and base64-encoded before being installed in `.env`. They are never typed manually.

### 2.3 Rotation

| Key class | Rotation cadence | Trigger for early rotation |
|---|---|---|
| HMAC keys (password-reset, OTP, storage-signing) | Annually | Suspected compromise; departure of a staff member with secret access; significant infrastructure change |
| Vendor API keys (Razorpay, Brevo, MS Graph, Zoom, OpenAI, S3) | Annually, or per the vendor's recommendation, whichever is sooner | As above |
| TLS certificates | 90 days (Let's Encrypt automatic via `certbot.timer`) | On revocation; key compromise |
| Future column-level encryption keys | 18 months or per regulator guidance | As above |

Rotation is documented in the Risk Register with the date, the new key fingerprint (not the key), and the operator.

### 2.4 Distribution

Keys are not shared via email, chat, or shared documents. The standard distribution method is:

1. The Engineering Lead generates the key on a TTII-issued laptop;
2. Installs it directly on the production droplet via SSH;
3. Records the rotation in the Risk Register.

Staff who later need read access to a key for an investigation request it from the Engineering Lead and the access is logged.

### 2.5 Destruction

When a key is rotated out, it is overwritten in the environment file and the file's previous version is deleted. There is no backup of historical keys (a leaked key cannot be revoked retroactively, but storing it permanently expands the attack surface).

## 3. Things explicitly disallowed

- Hard-coded secrets in source code, repository config, or container images;
- Sharing the same key across environments (production keys differ from staging and dev);
- Algorithms outside the approved set (DES, 3DES, RC4, MD5, SHA-1, ECB-mode anything);
- Custom cryptographic constructions ("I'll just XOR this with...");
- Storing private keys with insufficient file permissions (`0600` is the minimum);
- Logging secrets, even at `debug` level.

## 4. Cryptographic agility

When an algorithm is deprecated by NIST or the wider community, this policy is updated and the affected code paths are migrated. The scrypt → Argon2id migration, in particular, is on the roadmap pending a benchmark of compatibility cost.

## 5. Vendor-side cryptography

We rely on the cryptography of our processors for storage encryption at rest:

- DigitalOcean managed disk encryption;
- DO Spaces / S3 server-side encryption;
- Razorpay handles all payment-instrument cryptography (we never see card numbers);
- Microsoft, Zoom, Brevo, OpenAI: cryptography per their SOC 2 / ISO 27001 attestations.

The [Vendor Risk Management Policy](vendor-risk-management-policy.md) reviews each provider's cryptography posture annually.

## 6. Audit

- All cryptographic primitive usages are reviewed during code review (see [Secure SDLC Policy](secure-sdlc-policy.md)).
- A dependency scan runs on every release to detect known cryptographic library vulnerabilities.
- The DPO reviews the secrets inventory annually.
